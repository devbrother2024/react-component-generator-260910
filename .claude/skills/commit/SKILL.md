# commit: 변경사항 분석 후 컨벤션 커밋

현재 저장소의 변경사항을 분석해 의미 단위로 나누고, 단위마다 컨벤션에 맞는 한국어 커밋 메시지를 지어 바로 커밋한다. 이 스킬이 트리거됐다는 것 자체가 사용자의 커밋 지시이므로, 메시지 초안을 보여주고 별도로 승인을 기다리지 않는다. 목표는 "무엇을 바꿨는지"가 `git log`만 봐도 드러나는 커밋을 만드는 것이다.

## Step 1: 변경사항 분석

다음을 병렬로 실행해 현재 상태를 파악한다.

- `git status` — untracked 포함 전체 변경 파일 목록
- `git diff` (unstaged) 와 `git diff --staged` (이미 staged된 것이 있다면) — 실제 변경 내용
- `git log --oneline -20` — 기존 커밋 메시지 스타일이 있으면 그것을 우선 따른다 (예: 이미 영어 Conventional Commits로 통일돼 있다면 굳이 한국어로 바꾸지 않는다). 커밋 이력이 없거나 스타일이 일관되지 않으면 아래 기본 컨벤션을 따른다.

커밋 대상이 하나도 없으면(clean) 그대로 사용자에게 알리고 종료한다.

diff 내용을 읽을 때 `.env`, credentials, API 키 등 비밀 정보로 보이는 파일이나 라인이 있는지 확인한다. 있으면 커밋 대상에서 제외하고 사용자에게 알린다 — 파일명이 평범해 보여도 내용은 반드시 확인한다.

## Step 2: 논리적 단위로 분류

전체 diff를 하나의 커밋으로 뭉뚱그리지 않는다. 서로 다른 목적의 변경(예: 새 기능 추가 + 무관한 버그 수정 + 포맷팅)은 각각 별도 커밋으로 나눠야 `git log`와 `git blame`이 의미를 가진다. 판단 기준:

- 같은 목적/같은 기능을 향한 변경은 한 커밋으로 묶는다 (파일이 여러 개여도 괜찮다).
- 서로 관련 없는 변경(다른 파일, 다른 의도)은 분리한다.
- 설정 파일 추가, 린트 자동수정, 포맷팅처럼 성격이 다른 변경은 기능 변경과 분리한다.
- 이미 첫 커밋 전 단계(예: 프로젝트 초기 세팅 전체)처럼 자연스럽게 하나의 덩어리인 경우까지 억지로 쪼개지 않는다 — 과도한 분리도 노이즈다.

각 단위에 어떤 파일이 속하는지 명확히 정리해둔다. 이후 `git add <files>`로 단위별 staging에 쓴다.

## Step 3: 커밋 메시지 작성

각 단위마다 한국어로 커밋 메시지를 작성한다. 형식:

```
<type>: <요약>
```

필요하면 스코프를 붙인다: `<type>(<scope>): <요약>`.

**type 선택 기준**

| type | 언제 |
|---|---|
| `feat` | 새로운 기능/컴포넌트/API 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변화 없는 코드 구조 개선 |
| `chore` | 빌드/설정/의존성/잡무성 변경 (기능·버그 수정 아님) |
| `docs` | 문서만 변경 |
| `style` | 포맷팅 등 로직에 영향 없는 스타일 변경 |
| `test` | 테스트 추가/수정 |
| `perf` | 성능 개선 |

기존 `git log`에 다른 컨벤션(예: 대문자 시작, 다른 prefix 체계)이 확립돼 있으면 이 표보다 그 컨벤션을 우선한다.

**요약 작성 규칙**

- 무엇을 바꿨는지가 아니라 **왜/어떤 의미로** 바꿨는지가 드러나게 쓴다. `"코드 수정"` 같은 공허한 요약 대신 `"사용자 입력 검증 로직에서 빈 문자열 처리 누락 수정"`처럼 구체적으로.
- 한 줄 요약은 간결하게. 배경 설명이 꼭 필요하면 본문(빈 줄 다음 문단)에 덧붙이되, diff만 봐도 알 수 있는 내용은 적지 않는다.
- 여러 단위를 커밋할 경우 각 커밋 메시지는 해당 단위의 변경만 설명한다 — 다른 단위 내용을 섞지 않는다.

## Step 4: 바로 커밋

계획이 서면 사용자 확인을 기다리지 않고 단위별로 순서대로 실행한다:

1. `git add <해당 파일들>` — 해당 단위의 파일만 staging (전체를 뭉뚱그리는 `git add -A`/`git add .`는 피한다)
2. `git commit -m "$(cat <<'EOF' ... EOF)"` 형태로 커밋 (히어독으로 메시지 전달해 포맷 보존)
3. 각 커밋 직후 `git status`로 정상 반영 확인

커밋 메시지 끝에는 현재 세션에 지정된 attribution(예: `Co-Authored-By` 줄)이 있으면 그대로 포함한다.

모든 단위 커밋이 끝나면 결과를 요약해 보고한다: 몇 개의 커밋을 만들었는지, 각 커밋의 해시(짧은 형태)·메시지 한 줄·포함 파일. 사용자가 사전에 메시지를 보지 못했으므로 사후 요약은 생략하지 않는다. 메시지나 그룹핑이 마음에 들지 않으면 사용자가 `git reset`/`git commit --amend` 등을 요청할 수 있음을 인지하고, 그런 요청이 오면 그때 대응한다.

**하지 않는 것**

- `--no-verify`, `--no-gpg-sign` 등으로 훅/서명을 건너뛰지 않는다. pre-commit 훅이 실패하면 원인을 고치고 다시 커밋한다 (`--amend` 금지 — 훅 실패 시 커밋 자체가 안 된 것이므로 새 커밋으로 진행).
- 사용자가 push까지 요청하지 않은 이상 `git push`는 하지 않는다.
- 기존 커밋을 `amend`하지 않는다 (사용자가 명시적으로 요청한 경우 제외).
- 시크릿으로 의심되는 파일/라인이 있으면 자동 커밋 대상에서 제외하고, 그 사실만 사용자에게 알린다 — 이 경우는 승인 없이 그냥 건너뛰고 진행하되 왜 뺐는지 보고한다.

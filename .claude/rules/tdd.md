# TDD Rule

> ⚠️ 이 규칙은 **Rigid**하다 — 상황에 맞게 완화하거나 변형하지 마라. 예외가 필요하다고 느껴지면 규칙이 아니라 스스로를 의심하라.

## 1. 적용 기준

**TDD 필수 (반드시 테스트 먼저)**

- 비즈니스 로직 (계산, 상태 전이, 분기 처리 등 판단이 들어가는 모든 코드)
- API (엔드포인트 핸들러의 요청/응답 로직 — 라우팅 자체가 아니라 그 안의 처리 로직)
- 유틸리티 함수 (입출력이 명확한 순수 함수)
- 버그 수정 (버그를 재현하는 실패 테스트를 먼저 작성한 뒤 고친다)

**TDD 불필요**

- 타입 정의 (`interface`, `type`)
- 설정 파일 (빌드/린트/환경 설정 등)
- 순수 UI (로직 없이 마크업과 스타일만 있는 프레젠테이셔널 컴포넌트)
- SQL (스키마, 마이그레이션)

판단이 애매하면(예: 로직이 섞인 UI 컴포넌트) 로직 부분만 분리해 테스트 가능한 함수로 뽑고, 그 함수에 TDD를 적용한다. "UI라서 예외"는 성립하지 않는다.

## 2. RED-GREEN-REFACTOR 사이클

### RED

- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 욱여넣지 않는다.
- 테스트를 작성한 뒤 **반드시 실행해서 실패를 눈으로 확인**한다. 실행하지 않고 "당연히 실패할 것"이라 가정하지 않는다.
- 실패 이유는 **오직 "기능이 아직 구현되지 않았기 때문"**이어야 한다. 오타, import 누락, 문법 오류로 인한 실패는 무효 — 원인을 고치고 다시 RED부터 확인한다.

### GREEN

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI**: 지금 테스트가 요구하지 않는 기능은 만들지 않는다. "어차피 나중에 필요할 것 같아서" 미리 만드는 코드는 금지.
- 새 테스트뿐 아니라 **기존 테스트 전체가 통과**하는지 확인한다.

### REFACTOR

- 중복 제거, 이름 개선, 헬퍼 추출을 한다.
- 이 단계 내내 **테스트는 green을 유지**해야 한다. 한 번이라도 깨지면 즉시 되돌린다.
- **새로운 동작을 추가하지 않는다.** 리팩터링 중 "이것도 필요하네" 싶은 게 생기면 다음 사이클의 RED로 미룬다.

### 반복

- 다음 동작에 대한 **RED로 돌아간다.** 사이클을 건너뛰지 않는다.

## 3. 삭제 강제 규칙

- 테스트보다 프로덕션 코드를 먼저 작성했다면, **그 코드를 삭제하고 RED부터 다시 시작**한다.
- "일단 참고용으로 남겨둔다", "주석 처리만 해둔다"도 금지한다. **완전히 삭제**한다.

## 4. 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트가 필요 없다" | 단순한 코드일수록 테스트 작성 비용도 낮다. 비용이 거의 0인데 안 할 이유가 없다. 단순하다는 판단 자체가 틀렸을 때 테스트가 그 증거를 남긴다. |
| "나중에 추가하겠다" | 나중은 오지 않는다. 지금 GREEN 상태에서 테스트를 추가하는 비용이 가장 낮고, 시간이 지날수록 컨텍스트를 잃어 비용이 커진다. |
| "시간이 없다" | 테스트 없이 작성한 코드는 회귀 여부를 손으로 확인해야 하므로 오히려 더 오래 걸린다. 시간이 없을수록 TDD가 필요하다. |
| "삭제하면 낭비다" | 순서를 어긴 코드를 남기면 "테스트가 코드를 검증한 것"이 아니라 "코드에 맞춰 테스트를 끼워 맞춘 것"이 된다. 낭비는 코드가 아니라 잘못된 검증 순서다. |
| "프로토타입이다" | 프로토타입은 살아남아 프로덕션이 되는 경우가 대부분이다. 정말 버릴 코드라면 애초에 이 규칙의 적용 대상(1번 기준)이 아닌지부터 확인하라. |

## 5. 프로젝트별 규칙 우선 조항

이 문서는 **기본값(fallback)**이다. 현재 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 관련 규칙이 명시돼 있다면, **그 규칙이 이 문서보다 우선**한다. 프로젝트 규칙이 다루지 않는 부분에 한해 이 문서를 따른다.
